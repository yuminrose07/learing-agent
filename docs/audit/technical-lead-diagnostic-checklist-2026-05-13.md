# Learning Agent 技术负责人视角项目诊断清单

> **文档目标**：从技术负责人视角，对当前 Learning Agent 项目的工程成熟度、架构风险、交付优先级与下一阶段治理重点做一次可执行诊断。  
> **诊断日期**：2026-05-13  
> **诊断方式**：静态阅读 `learning_agent/` 核心代码、`docs/` 设计与审计文档、`tests/` 测试样例，并结合当前项目设计原则进行归纳。  
> **适用对象**：项目作者、未来协作开发者、后续 AI 编码助手。  
> **说明**：本清单偏“负责人治理视角”，不是逐行 Bug 报告；重点是判断当前项目处于什么阶段、最该优先补哪些能力、哪些风险会阻塞后续演进。

---

## 一、TL;DR

当前项目已经不是“Demo 阶段”，而是进入了 **Agent Runtime 骨架已成形、能力层尚未完全接线** 的阶段。

一句话判断：

> **核心运行时方向正确，可靠性意识明显强于功能堆砌，但系统仍处于“骨架成熟、肌肉未长齐”的过渡期。**

当前最重要的不是继续横向加功能，而是先完成以下三个闭环：

- **闭环 1：核心循环与扩展接线闭环**
  - 保证 Hook、事件、扩展声明的能力真实生效，而不是“代码存在但没有接上主流程”。
- **闭环 2：记忆系统与 Agent 行为闭环**
  - 让 `MemoryManager / KnowledgeGraph / SpacedRepetition` 真正影响上下文构建、对话策略和复习流程。
- **闭环 3：CLI / Web / 文档 / 测试闭环**
  - 保证不同入口行为一致、设计文档与代码一致、测试覆盖真实关键路径。

## 二、项目阶段判断

### 当前所处阶段

我将当前项目定位为：

**阶段 2.5：Runtime-first 的早中期工程化阶段**

特征如下：

- 已有明确架构哲学，而不是边写边猜。
- 已形成核心分层：`provider / core / session / memory / agent / extensions / web`。
- 已出现“可靠性驱动”的设计：重试、降级、状态快照、事件流、观测、工具校验、权限守卫。
- 已有专题设计文档、Bug 文档、实现归档文档，说明项目开始具备工程自我管理能力。
- 但能力层仍未完全闭环，尤其是记忆系统、知识提取、事件驱动扩展接入仍不完整。

### 当前不宜误判为

以下判断都偏乐观：

- 不是“功能完整的可长期使用 Agent”
- 不是“记忆驱动型学习 Agent 已完成”
- 不是“Web/CLI 双端一致的稳定产品”
- 不是“扩展系统已可放心承载大规模新增功能”

## 四、技术负责人核心诊断结论

### 1. 当前最强的资产不是功能，而是 Runtime 骨架

最值得保护的部分是：

- `AgentLoop` 的会话级运行时模型
- 工具调用的校验、失败追踪、降级链路
- 事件、Hook、Observability 的底层骨架
- 文档驱动的演进方式

负责人视角建议：

- 后续所有重构，都应以“不破坏 runtime 连续性”为第一约束。
- 宁可暂缓新能力，也不要轻易破坏 `AgentLoop + SessionRuntime + Observability` 这一套骨架。

### 2. 当前最大的问题不是“没有设计”，而是“设计落地还没完全接通”

项目已经存在不少优秀设计：

- 记忆分层
- 扩展系统
- 自愈与持续运行
- Provider 韧性包装
- Web 运行时清理
- Tool result 一致性修正

但负责人视角最关心的是：

> **这些设计是否已经变成真实行为，而不是只存在于模块或文档中。**

当前存在明显“设计已存在、主流程未闭环”的区域：

- `AFTER_RESPONSE` 修改结果是否真正影响最终输出
- `agent.responseDone` 是否真正发出
- `ask_mode` 是否在 Web 入口完整透传
- `ResilientProvider` 是否已真正进入系统装配链
- `MemoryManager` 是否真实参与上下文构建与知识生命周期

### 3. 当前的主要风险不是崩溃，而是“虚假完成感”

这是一个很典型的早中期风险：

- 文件很多
- 模块很多
- 设计文档很多
- 测试看起来也不少

但真正从产品行为看，仍有若干关键闭环没有打通。

负责人视角必须防止以下误区：

- 误以为“有模块”就等于“能力已完成”
- 误以为“有扩展”就等于“扩展已接上线”
- 误以为“有记忆系统”就等于“Agent 真的在使用长期记忆”
- 误以为“有 Web API”就等于“CLI 和 Web 行为一致”

## 五、诊断清单

以下清单按负责人优先级排序，建议每一项都明确“状态 / owner / 计划日期 / 验证方式”。

### A. 核心运行时

- [ ] `AgentLoop` 是否仍是系统最小必要核心，且职责边界清晰
- [ ] 每个 session 的运行时状态是否完全隔离
- [ ] 同一 session 的并发访问是否被严格串行化
- [ ] session 删除、重置、过期后，运行时对象是否能被清理
- [ ] 出错后是否优先修复/降级，而不是直接终止会话
- [ ] 所有兜底链路是否也具备重试或稳定收尾能力
- [ ] 工具调用中断时，历史消息协议是否仍保持完整
- [ ] 长对话下上下文控制是否有稳定策略，而不是被动溢出

### B. 扩展系统

- [ ] 所有内置扩展是否都已真正接入主循环
- [ ] Hook 返回 `modified=True` 时，修改结果是否被主流程消费
- [ ] Hook 的失败是否只影响扩展，不影响核心持续运行
- [ ] 是否存在“订阅了事件但主流程并未发出该事件”的情况
- [ ] 扩展的职责是否仍保持在“策略层”，未侵入核心层
- [ ] Hook 是否需要超时保护，防止扩展卡死核心流程
- [ ] 扩展优先级是否有统一约定，避免后续冲突

### C. 记忆系统

- [ ] `MemoryManager` 是否已经真实参与上下文构建
- [ ] `relevant_recall()` 是否被核心对话流程调用
- [ ] L1 → L2 → L3 生命周期是否有真实触发路径
- [ ] 知识确认、复习调度、掌握度更新是否形成闭环
- [ ] 记忆写入是否有去重、质量控制和来源追踪
- [ ] 记忆系统是“展示层数据”还是“决策层数据”，是否已明确
- [ ] 当前记忆能力是否足以支撑“学习型 Agent”的产品定位

### D. Provider 与韧性层

- [ ] 系统实际运行时是否已接入 `ResilientProvider`
- [ ] Provider 异常分类是否足够稳定，不会误重试
- [ ] 熔断、Fallback、重试是否真的在生产路径生效
- [ ] 最终兜底链路是否仍依赖单点 Provider
- [ ] 模型切换是否只改 Provider 层，不影响上层逻辑
- [ ] Provider 层错误是否被翻译成统一语义，而不是泄露底层异常细节

### E. Tooling 与权限治理

- [ ] Tool schema、参数校验、执行结果三者是否始终一致
- [ ] 工具失败是否区分 validation / permission / execution 三类语义
- [ ] Tool result 是否有大小限制，避免污染上下文
- [ ] 工具权限守卫是否符合“默认不随意 abort”的项目原则
- [ ] Ask / Deny / Allow 三类行为在 CLI 和 Web 中是否体验一致
- [ ] bash / file 工具是否既可控又不会过度阻断正常开发流程

### F. Web / CLI 一致性

- [ ] Web API 与 CLI 是否共享同一套核心行为，而不是两套逻辑
- [ ] `ask_mode`、session fork、confirm、save 等能力是否双端一致
- [ ] Web 端是否存在参数未透传、状态未持久化、异常未收口的问题
- [ ] SSE 流式输出协议是否稳定，能覆盖 tool_call / finish_reason / error
- [ ] Web 删除 session、重置 runtime 后，系统内部状态是否真的一致

### G. 可观测性

- [ ] 关键状态变化是否都有事件记录
- [ ] trace、span、runtime 状态是否能定位关键故障
- [ ] 可观测性是否优先服务“定位问题”，而不是只做展示
- [ ] 是否存在“日志很多，但无法回答为什么失败”的情况
- [ ] 错误日志、审计日志、trace 日志之间是否可互相关联
- [ ] 是否已经能支持一次真实问题的端到端排障

### H. 测试治理

- [ ] 当前测试是否覆盖真实 P0 风险，而不仅是局部函数
- [ ] 是否有“主流程闭环测试”，覆盖 user → llm → tool → result → persist
- [ ] 是否有 Web/CLI 行为一致性的测试
- [ ] 是否有扩展接线完整性的测试
- [ ] 是否有记忆系统真正参与 prompt 的行为测试
- [ ] 测试是否在验证“系统持续运行”，而不是只验证单点函数正确

### I. 文档治理

- [ ] 设计文档是否仍与代码实现一致
- [ ] 每次较大变更后是否都有 `docs/output/` 归档
- [ ] Bug 文档是否能回溯到设计和实现总结
- [ ] 是否已经形成“设计 -> 实现 -> 验证 -> 归档”的稳定工作流
- [ ] 是否存在文档说已实现，但代码行为并未闭环的情况

## 六、负责人视角的 P0 / P1 / P2 优先级

## P0：必须先收口，否则后续继续扩功能会放大成本

### P0-1. 核心接线一致性收口
目标：

- 清点所有关键 Hook、事件、扩展，确认“声明能力”与“实际执行路径”一致。

关注点：

- `AFTER_RESPONSE` 修改结果是否真实生效
- `agent.responseDone` 是否真实发出
- Web `ask_mode` 是否完整透传
- 关键扩展是否只是注册了，但没有行为闭环

交付标准：

- 列出一份“扩展接线矩阵”
- 每个关键 Hook 和事件都能在主流程中找到实际入口和验证方式

### P0-2. 记忆系统接线策略定稿
目标：

- 明确记忆系统到底走“核心集成”还是“扩展集成”。

必须回答的问题：

- `relevant_recall()` 在哪里进 prompt
- 候选知识在哪里产生
- 知识确认后如何晋升
- 复习调度何时触发
- 这些流程哪些属于核心，哪些属于扩展

交付标准：

- 形成一份设计文档
- 文档与代码接入点一一对应

### P0-3. Provider 韧性链路真正上线
目标：

- 决定是否正式将 `ResilientProvider` 置于生产调用链中。

交付标准：

- 初始化装配链明确
- 测试覆盖真实 fallback / retry / breaker 行为
- 文档同步说明当前启用状态

---

## P1：完成产品化最小闭环

### P1-1. Web / CLI 行为统一
- 对齐 chat、ask、fork、confirm、save、runtime reset 等核心能力
- 补双端一致性测试
- 确保不同入口不会出现“同名功能，不同行为”

### P1-2. 工具上下文污染治理
- 对超大 tool result 做截断与摘要
- 明确哪些结果要进入会话历史，哪些只进入观测层
- 防止工具输出吞掉上下文预算

### P1-3. Hook 超时与扩展失效隔离
- 给 Hook 加超时
- 约束扩展故障的传播范围
- 继续强化“扩展失败不拖死核心”的原则

---

## P2：中期能力建设

### P2-1. 真正的学习型 Agent 行为
- 让长期记忆、复习、掌握度进入真实交互
- 让系统从“带记忆模块的聊天 Runtime”升级为“记忆驱动的学习 Agent”

### P2-2. 更明确的 Session 生命周期治理
- 会话压缩
- 分支摘要
- 老 session 冻结与恢复策略
- 运行时与持久化数据的边界进一步清晰化

### P2-3. 更强的运维视角观测
- 观测面板聚焦“能定位问题”
- 形成 session 级、trace 级、tool 级的统一排障视图

---

## 七、建议的治理动作

### 未来两周建议只做三件事

1. **做一份扩展接线审计表**
   - 逐项列出 Hook / Event / Extension / Trigger / Consumer / Test 状态

2. **补一份记忆系统接入设计文档**
   - 决定记忆哪些进核心、哪些留扩展
   - 不再让 `memory/` 处于“代码存在但行为未闭环”的状态

3. **完成 Web/CLI 一致性收口**
   - 先统一核心行为，再继续扩前端能力

### 暂不建议优先做的事

- 暂不建议继续新增大量工具
- 暂不建议继续铺更多 Web 可视化页面
- 暂不建议扩更多学习模式
- 暂不建议过早做复杂多 Provider 支持
- 暂不建议把图谱、向量检索、多模态一起并行推进

原因很简单：

> 当前真正限制项目质量上限的，不是功能数量，而是“主链路闭环程度”。

## 八、负责人结论

如果我是这个项目的技术负责人，我会给出这样的判断：

### 这个项目值得继续投入
因为它已经具备三个稀缺特征：

- 有稳定的架构价值观
- 有明显的可靠性意识
- 有文档驱动的工程演进习惯

### 这个项目当前不该做“功能扩张”
因为核心问题不是“不会做更多”，而是“已有能力没有完全闭环”。

### 这个项目下一阶段的成功标准
不是新增多少模块，而是做到以下三点：

- **系统声明的能力，真实存在**
- **核心设计文档，与运行时行为一致**
- **学习 Agent 的关键差异化能力，真正进入主循环**
